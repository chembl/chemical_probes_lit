# Running the literature pipeline with external data

The public repository contains the analysis code. Keep downloaded inputs, run outputs,
and your institutional Slurm scripts outside the checkout. You only need one Git
repository; the private scripts folder is an ordinary directory on your cluster.

## Storage layout

```text
/project/chemical_probes/
├── code/                       # This repository checkout (can be elsewhere)
├── cluster/                    # Private .sh scripts, environment setup, settings
├── inputs/
│   ├── probesSubset.csv        # HQ dictionary: tab-separated despite its suffix
│   ├── dated_evidence/         # Extracted parquet subdirectories, one per source
│   ├── disease_term_black_list.tsv  # Plotting input: comma-separated
│   ├── probe_references.csv    # Plotting input: comma-separated
│   └── opentargets/snapshot_001/
│       ├── literature_match/
│       ├── association_by_datasource_indirect/
│       ├── disease/
│       ├── clinical_target/
│       ├── clinical_indication/
│       └── download_manifest.json
└── runs/analysis_001/
    ├── intermediate/
    ├── results/
    ├── figures/
    ├── tables/
    └── logs/
```

Use your institution's actual project-storage path. Inputs and outputs must be
accessible from compute nodes; the Spark merge helper uses ordinary filesystem
paths, not `s3://`, `gs://`, or HDFS URIs. Keep `cluster/` on backed-up storage;
files there have no Git history. Do not place it inside the public checkout.

## Environment and path setup

Install dependencies from the repository's `requirements.txt` into an external
Python environment, and activate it before running commands. Spark also requires
a compatible Java installation. The requirements file currently pins PySpark 4.1.2;
the historical manuscript environment used PySpark 3.3.1 and Python 3.11.7.
Those are different environments: this path refactor does not establish that their
results or compatibility are equivalent. Use a validated cluster environment for
production, and record its versions.

Set these variables in your shell, or in a private file such as
`/project/chemical_probes/cluster/paths.sh` that each job sources:

```bash
export CODE_DIR="/project/chemical_probes/code"
export INPUT_DIR="/project/chemical_probes/inputs"
export OT_DIR="$INPUT_DIR/opentargets/snapshot_001"
export RUN_DIR="/project/chemical_probes/runs/analysis_001"
export PROBES_FILE="$INPUT_DIR/probesSubset.csv"
export DATED_EVIDENCE_DIR="$INPUT_DIR/dated_evidence"

mkdir -p "$OT_DIR" "$RUN_DIR"/{intermediate,results,figures,tables,logs}
```

Replace the example paths before executing. An existing checkout can stay where
it is: set `CODE_DIR` to its absolute path. These variables are expanded by the
shell in the commands below; Python steps do not automatically read them.
Use a new `RUN_DIR` for each analysis, and a new snapshot directory for a fresh download.

All steps require an explicit destination (`--output`, or `--output-dir` for step 0).
Parents are created automatically. Relative paths are relative to the current
working directory; absolute paths are recommended. Existing output files are
replaced, so do not run two jobs against the same output filename. Spark TSV merge
parts use unique temporary directories beside the output and are cleaned up after
normal success or failure. Allow disk space for both part files and the merged TSV.
Spark's own spill/cache storage is separate and should be configured through your
cluster's Spark environment, for example `SPARK_LOCAL_DIRS` for local-mode jobs.

## Inputs that must be prepared separately

Step 0 downloads only the five Open Targets datasets shown above. You must also
provide:

- The HQ probes dictionary built using `3_probesHQ/probes_hq_dataset.ipynb`.
  It is tab-separated and includes `CHEMBLID`, `SYNOMS`, `GENE`, and the other
  probe metadata used by the pipeline. Export/copy it to `PROBES_FILE`.
- Dated evidence from the source linked in the root README, extracted into a
  directory with parquet subdirectories for the individual evidence sources.
- For the plotting notebook, the curated disease exclusion list and probe
  reference table. These are not generated by steps 0–7. Preserve the filenames
  shown above, or edit the notebook's corresponding input paths. The exclusion
  list must contain `diseaseId`; both files are read as comma-separated tables.

## Execute steps 0–7 in order

Run the following commands in the configured Python environment, on suitable
allocated compute resources. Every command can be executed from any directory.
Run each step only after its predecessor succeeds. `--help` describes its arguments
without starting Spark or downloading data.

### 0. Download Open Targets inputs

```bash
python "$CODE_DIR/2_probesLit/0_download_OT_files.py" \
    --output-dir "$OT_DIR" \
    --release 26.09 \
    --literature-release latest
```

These defaults select release `26.09` for
association/disease/clinical data and `latest` for literature. `latest` changes over
time. For reproducibility, choose a literature release where the required dataset
is available, or supply its complete server directory using `--literature-dir`.
Directory layouts can differ between releases; an unavailable path causes the download
to fail. This change does not verify upstream availability or schema compatibility.

The downloader writes `download_manifest.json` after all five downloads succeed,
recording requested releases, source URLs, filenames and completion time. It does not resolve
`latest` to a fixed release or calculate checksums. Retain the downloaded snapshot
and record checksums separately if exact input identity is required. Downloads
replace same-named local files. Stale parquet filenames are rejected; interrupted
files are retried from the beginning rather than resumed. Use an empty destination
for a new snapshot. All five listings are validated before any data files are fetched.
Use `--check-only` with the same arguments to validate listings without downloading.
Files are streamed to `.part` files and renamed only after successful transfers.

### 1. Find articles mentioning HQ probes and retain their annotations

```bash
python "$CODE_DIR/2_probesLit/1_get_ner_hq_probes.py" \
    --matches "$OT_DIR/literature_match" \
    --probes "$PROBES_FILE" \
    --intermediate-output "$RUN_DIR/intermediate/epmc_ner_results_hq_probes.tsv" \
    --output "$RUN_DIR/intermediate/1_epmc_ner_results_hq_probes_all_sent.tsv"
```

The intermediate file contains HQ probe mentions; the final file contains all
annotations for those articles. If omitted, `--intermediate-output` defaults to
`<output>.hq_mentions.tsv`. It must differ from the final output path.

Step 1 expects the public `literature/match` parquet schema with `pmid`, `label`,
`mappedId`, `type`, `pubDate`, `section`, and `text`. It exports **`mappedId` as
`label_id`**, so downstream TSV column names and step 2 arguments are unchanged.
`mappedId` is already one mapped entity ID per row; do not explode `entityIds`
again. Distinct mapped IDs for the same mention are retained, while identical
projected rows are deduplicated as before. No new `isMapped`/`isValid` filtering
is introduced: use the public valid-match dataset, not failed matches. Legacy
inputs containing only `keywordId` fail with an explicit schema error.

## Private Slurm jobs: no second repository

Create `/project/chemical_probes/cluster/step2.sh` on the cluster, outside the Git

to your institution. Put account/partition directives only in your private file.

```bash

#SBATCH --job-name=probes-step2
#SBATCH --cpus-per-task=6
#SBATCH --mem=32G
#SBATCH --time=02:00:00
set -euo pipefail

cd "$RUN_DIR"

python "$CODE_DIR/2_probesLit/2_get_triplets.py" \
    --input "$RUN_DIR/intermediate/1_epmc_ner_results_hq_probes_all_sent.tsv" \
    --probes "$PROBES_FILE" \
    --output "$RUN_DIR/intermediate/2_ner_probes_triplets.tsv"
```

Source your paths in the submission shell and create the log directory **before**
submission, because Slurm opens logs before the job's shell commands execute:

```bash
source /project/chemical_probes/cluster/paths.sh
mkdir -p "$RUN_DIR/logs"
sbatch --output="$RUN_DIR/logs/step2-%j.out" \
       --error="$RUN_DIR/logs/step2-%j.err" \
       /project/chemical_probes/cluster/step2.sh
```

Repeat this pattern with the matching command for each step. The resource values
above are illustrative for step 2, not the Spark steps. Steps 1 and 4–7 retain the
existing 200g driver/executor memory settings; request sufficient memory and configure
Spark CPU usage to fit your allocation. The historical step 1 job used 24 CPUs and
at least 250 GB RAM. Do not execute those jobs directly on the login node.

For separate jobs, submit successors using `--dependency=afterok:JOB_ID`, replacing
`JOB_ID` with the predecessor's job ID. For example, once step 2 is submitted:

```bash

       --output="$RUN_DIR/logs/step3-%j.out" \
       --error="$RUN_DIR/logs/step3-%j.err" \
       /project/chemical_probes/cluster/step3.sh
```

Use the same run paths throughout a chain and do not edit them while jobs are queued.
Step 0, step 3 and script 8 need network access; use your institution's permitted
transfer/compute setup. Slurm script syntax and job dependencies are documented in
[the official sbatch reference](https://slurm.schedmd.com/sbatch.html).

## Clinical datasets migration (26.09)

`known_drug` has been retired. Step 0 now downloads five datasets over **HTTPS**,
including `clinical_target` and `clinical_indication`; it does not download
`clinical_report`, because trial status is not used by this analysis. Directory
listings are checked before downloads, and each transfer is retried on network
failure. A successful listing does not establish schema compatibility: step 7
validates required columns and rejects unrecognised stage labels.

Step 7 now requires `--clinical-target` and `--clinical-indication` instead of
`--otdrug`. It extracts distinct `drugId,targetId` links from Clinical Target,
ignoring its disease array and its across-indication maximum. It joins these links
to mapped `drugId,diseaseId,maxClinicalStage` rows in Clinical Indication. Thus a
drug's stage for disease A is never used as its stage for disease B. This is a
mechanism-of-action-based target attribution, not proof that a trial isolated that
target's effect. Unmapped drug/disease identifiers cannot be joined and are omitted.

For each target–disease pair, the highest-ranked disease-specific stage wins;
ties select the lexicographically first drug ID for a reproducible representative.
The output preserves the input rows and adds:

| Column | Meaning |
| --- | --- |
| `drugId` | Representative drug at the highest stage for the pair |
| `maxClinicalStage` | Original indication stage label |
| `clinicalStageRank` | Explicit ordering, **not a numeric trial phase** |
| `hasClinicalIndication` | Whether a mapped drug indication was joined |

The old `phase` and unused `status` columns are removed. No matched indication has
null drug/stage/rank and `hasClinicalIndication=false`. A mapped indication with a
missing stage is retained as `UNKNOWN` (rank 0), not treated as absence of evidence.
The notebook excludes **all matched indications**, including UNKNOWN and preclinical,
from its strict no-drug-evidence subset. It displays category labels rather than
mislabeling ranks as phases. Its separate ChEMBL chemical-probe `maxPhase` analysis
is unchanged. Re-run steps 7 and 9 before running the updated notebook.

Ordering (low to high): UNKNOWN, PRECLINICAL, IND, EARLY_PHASE_1, PHASE_1,
PHASE_1_2, PHASE_2, PHASE_2_3, PHASE_3, PREAPPROVAL, PHASE_4, APPROVAL,
WITHDRAWAL. The supplied indication labels are preserved; we do not recompute
Open Targets' aggregation. Their documentation describes mapping supporting
PHASE_4/WITHDRAWAL evidence to aggregate APPROVAL. This is a historical development
summary, not a guarantee of current authorisation or trial status.

Sources: [clinical stages and sources](https://platform-docs.opentargets.org/drug/clinical-report),
[Clinical Indication aggregation](https://platform-docs.opentargets.org/disease-or-phenotype/drugs),
[Clinical Target scope](https://platform-docs.opentargets.org/target/drugs),
[upstream schemas](https://github.com/opentargets/clinical_mining/blob/main/src/clinical_mining/schemas.py).
The actual 26.09 parquet schemas and clinical listing availability still need to
be checked on the cluster; the implementation fails explicitly if required fields
or files are missing. Updating data sources changes coverage and counts relative
to historical Known Drugs analyses.

To check download availability before submission, run script 0 with the same
release/output arguments and `--check-only`. This fetches only listings. Use a fresh
snapshot for a different release. An old `known_drug` folder is never read by the
updated pipeline.

## TSV quoting and migration of older outputs

Pipeline TSV files now use double quotes around fields containing special characters,
and double embedded quotes (`""`) rather than backslash-escaped quotes. Backslashes
in labels and LaTeX remain literal. Spark readers use multiline parsing with the
same dialect; pandas uses its default quoting with `sep="\t"` and no `escapechar`.
Step 2 uses a CSV writer rather than manually concatenating fields, preserving tabs
and newlines inside sentences. Spark output also preserves leading/trailing spaces.

**Regenerate step 1 outputs from the downloaded parquet after this change**, then
rerun step 2 and subsequent steps. Older Spark TSV exports used a different dialect;
do not mix old and new outputs or use `escapechar="\\"` to compensate. That setting
can consume a literal trailing backslash and merge two fields. No malformed rows
are skipped. The Spark round-trip regression can be run with `RUN_SPARK_TESTS=1`
in an environment with Java/PySpark; the default suite tests step 2 text preservation.

## Association schema and dated-evidence coverage (26.09)

Step 4 now selects `aggregationType == "datasourceId"`, maps `aggregationValue`
to `datasourceId`, and exports `associationScore` as `score`. It reconstructs
`datatypeId` from the public Open Targets pipeline's `datasource_weights` mapping.
The source URL and configuration SHA-256 are recorded in `association_schema.py`.
This mapping was checked against the public configuration, **not a release-tagged
26.09 configuration**. It covers all 20 sources observed in the supplied 26.09
schema inspection. Unknown datasource IDs fail explicitly and must be reviewed;
no unknown source is silently dropped or assigned a guessed datatype.

[Mapping source](https://github.com/opentargets-archive/pts/blob/main/config.yaml).
`known_drug` is still a datatype label for `clinical_precedence`; that does not
mean the retired `known_drug` dataset is downloaded. Association timeseries are
not substituted for the older curation/publication/study dates.

Step 5 joins only exact `diseaseId,targetId,datasourceId` keys. In particular it
**does not alias** `clinical_precedence` to `chembl` or `gwas_credible_sets` to
`ot_genetics_portal`. The older dated-evidence snapshot is not equivalent to 26.09.
The output adds `datedEvidenceStatus`:

- `no_association`: the literature row has no matched association datasource.
- `source_absent`: the datasource does not occur in the dated-evidence input.
- `pair_absent`: that source exists, but no dated row matches this target/disease.
- `dates_missing`: a dated row matches but contains no usable year values.
- `matched`: at least one year is available.

Missing years remain null. Year lists are sorted, deduplicated and serialized as
JSON arrays for TSV output, preserving the notebook's list-text interface. Missing
or non-integer year values do not become invented dates. All step 4 rows are
preserved. A companion `<output>.dated_coverage.json` records the input location,
join policy and counts by datasource/status over unique association keys. It is
written during the coverage check; job success and the final TSV must still be
checked separately. Inspect this report before temporal analyses: a missing date
is not evidence that an association did not exist. Even identical source IDs do
not guarantee equivalent coverage across releases. Temporal plots based on the
older snapshot describe only the subset with available dates.

The existing step 4 and step 5 CLI arguments are unchanged. Update the cluster
checkout and rerun step 4, then step 5. Steps 1–3 and downloads need not be repeated.

## Large-file article annotation (script 8)

Script 8 processes the step 7 TSV in two passes, without loading the full dataset
or all unique PMIDs into memory. Pass 1 collects unique valid numeric PMIDs into a
SQLite cache; PubMed lookups run in batches of 200 with timeouts, retries and rate
limiting. Each batch is committed, so restarting reuses successful classifications
and retries unresolved IDs. Pass 2 adds `articleType` in chunks and preserves the
original field text, row order and row count. Quotes, backslashes, tabs and embedded
newlines use the shared TSV convention.

```bash
python "$CODE_DIR/2_probesLit/8_classify_article_types.py" \
    --input "$RUN_DIR/results/7_ner_probes_triplets_ptpairs_dr.tsv" \
    --output "$RUN_DIR/results/9_ner_probes_triplets_reviews.tsv" \
    --cache "$RUN_DIR/results/pubmed_article_types.sqlite" \
    --chunk-size 10000
```

The cache defaults to `<output>.pubmed.sqlite`. Use the same cache when restarting;
use a new cache to refresh previously successful PubMed classifications. Do not run
multiple writers against the same cache/output. Keep the input unchanged during the
run. The output is written to a temporary sibling and published only on completion;
an existing final output survives a failed run. Output writing restarts from the
beginning, while completed API lookups resume. A force-killed job may leave an orphan
`.part` file; remove it only after confirming its job has stopped.

Failed, missing, invalid or unclassifiable PubMed records leave `articleType` blank,
not `primary`. The completion log reports unresolved IDs and unclassified rows; a
successful job may still have incomplete API coverage. As before, `primary` means a
returned nonempty publication-type list without the exact `Review` label, not a
validated primary-research study design. Interpret or exclude unknown classifications
explicitly in subsequent analyses. The plotting notebook still has its own memory
requirements; this change only bounds script 8's working data.

For the current 89 GB input, start with a 32 GB Slurm allocation and reduce
`--chunk-size` if necessary. Memory depends on row width; this is not a guarantee.
Allow space for a complete additional TSV, the SQLite cache and its temporary tables.

PubMed rate limiting: script 8 now waits 1.1 seconds after each request and tries
up to five times per batch. HTTP 429 triggers waits of 30, 60, 120, 240 and 480
seconds, or longer if the server's `Retry-After` header requests it. Shared cluster
network traffic can still cause throttling. After a run with unresolved IDs, reuse
the same cache to retry them; successful entries are not queried again. The two
TSV passes and output writing are still repeated. Missing records may remain
unresolved even when requests succeed; do not interpret blanks as primary articles.
